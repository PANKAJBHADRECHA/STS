# Audit and architecture decision (2026-11-25)

The existing project contains three distinct systems: a deterministic task/controller research lab, a working LFM2.5-Audio turn-based application, and a smaller F-Actor native-duplex experiment. The 56 earlier unit/API/checkpoint tests and recorded-audio reports establish useful components, but did not establish a physical full-duplex conversation. The LFM worker buffers a complete utterance before inference, limits context to six turns, and is explicitly turn-based. The F-Actor server feeds simultaneous streams but has no meaningful interruption recovery, no acoustic echo cancellation and a best measured processing/audio ratio of 1.94 on this 8 GB M2. Those are structural limitations, not issues that a smaller HTTP buffer would fix.

The hardware audit found an Apple M2 MacBook Air (Mac14,2), eight CPU cores, 8 GiB unified memory, and built-in microphone/speakers. A later process audit also found the old LFM worker still resident during initial cascade tests. It was unloaded before further comparisons. Other user applications were left running. Earlier measurements taken with the competing worker remain development baselines, not controlled hardware comparisons.

## Alternatives

**Native Moshi/PersonaPlex:** simultaneous learned audio streams preserve vocal information, but the existing q4 and q2 Moshi probes failed badly under memory pressure. PersonaPlex access is authorized, but access does not remove its footprint. Re-running its large download is not the first optimization to make on this Mac. The [Kyutai implementation](https://github.com/kyutai-labs/moshi) and [PersonaPlex model](https://huggingface.co/nvidia/personaplex-7b-v1) remain the sources for those architectures.

**F-Actor/Mimi:** approximately 1.27 GB packed weights and 20 completed native audio cases show a feasible footprint, but the model misses correction grounding and generates unrelated dialogue. Pipeline changes improved its throughput but did not reach real time. This is not a suitable primary assistant. Its [model](https://huggingface.co/JSALT2026-Conv-AI-Simulator/f-actor-mimi-behavior-sd) and [implementation](https://github.com/MaikeZuefle/f-actor) are preserved as research references.

**Dessa:** [Block's own page](https://block.xyz/dessa) describes an audio-only, learned full-duplex model and specifies a MacBook Pro M4 Max or better for local inference. It presents demonstrations and access requests; no usable M2 checkpoint was found there. Vocal nuance is an important advantage of its architecture, but the published hardware target and availability do not make it a drop-in solution for this Mac. No Dessa weights were downloaded or benchmarked.

**Streaming cascade:** independent incremental ASR, a compact text-trained language model, and streaming neural synthesis permit continuous listening during playback while preserving the text model's instruction-following. This loses some audio-native prosody information and does not learn conversational timing end to end. It can nevertheless provide genuine full-duplex communication when capture, recognition, playback and interruption cancellation actually overlap. Simply shortening turn delays would not establish this.

[Moonshine's streaming API](https://github.com/moonshine-ai/moonshine/blob/main/docs/using/transcription.md) supplies incremental transcripts; its C++/ONNX [TTS API](https://github.com/moonshine-ai/moonshine/blob/main/docs/using/text-to-speech.md) supports streamed text and cancellation. We benchmark Tiny and Small streaming ASR rather than substituting recorded-file transcription. [MLX-LM](https://github.com/ml-explore/mlx-lm) supplies Metal generation and its existing prefix-cache implementation, including safety checks for recurrent caches. [Qwen3.5 0.8B](https://huggingface.co/mlx-community/Qwen3.5-0.8B-4bit) and [2B](https://huggingface.co/mlx-community/Qwen3.5-2B-4bit) are the compact reasoning candidates. Their setup pins exact revisions; serving loads only local paths. Local Piper and Kokoro voices offer a measured latency/expressiveness choice. No paid or hosted inference is involved.

## Audio and interruption design

A native CoreAudio duplex callback continuously captures 20 ms microphone frames and supplies a sample-synchronous reference of the assistant's actual rendered output. The browser is the control/history interface; browser capture experiments were removed from the selected path. [SpeexDSP](https://www.speex.org/docs/manual/speex-manual/node7.html) performs acoustic echo cancellation and residual suppression. WebRTC VAD identifies speech candidates. A candidate suppresses playback before ASR prefill, and recognized new words cancel it. Echo-like recognition is rejected rather than becoming a new user turn. The physical baseline exposed why energy-only cancellation was insufficient: speaker output could cancel its own reply.

ASR runs independently of the language model and TTS. Cancellation increments an epoch; the engine and native render queue reject stale output, including chunks that finish synthesizing after an interruption. The microphone does not stop during speech generation or playback. Context retains user requests and completed, rendered assistant phrases; an incomplete phrase is conservatively omitted after cancellation. Device rendering acknowledgements do not prove human hearing. Older context is summarized locally, with recent corrections retained verbatim.

Input and output queues, the language-model cache and context are bounded. A stopped or disconnected microphone closes the session. The UI shows listening/speaking status, supports immediate manual interruption, and keeps its conversation history only in the page. Raw test audio stays under the ignored runtime directory. Reports distinguish file probes, acoustic hardware tests and human participation; no human naturalness rating is inferred from ASR accuracy.

Measured outcomes and final model selection are recorded separately after the combined tests. Component throughput alone is not a full-duplex qualification or a sub-500 ms response claim.

## Additional rejected candidates

An Apple SpeechAnalyzer command-line probe found the language supported but its required assets unavailable; installation returned a framework error. It was not integrated. A Parakeet 0.6B MLX probe loaded in 48.8 seconds but returned empty text on both saved physical captures (5.31 and 0.65 seconds inference). Its extra memory/dependencies were excluded from the selected application. These failed probes do not establish the models' general quality; they did not solve this captured-input failure.

All combined measurements were on battery with macOS Low Power Mode enabled. No power policy was changed. The final acoustic repeat temporarily used output 70/input 50, then restored output 44/input 27/muted. It still misrecognized the spoken fixture. Synthetic speech recaptured from the same built-in speakers is not equivalent to a live human; neither a pass nor a failure licenses a human-conversation claim.

## Runtime storage correction

During final qualification, macOS offloaded Python files inside Documents and blocked module reads. The new environment was rebuilt under `~/Library/Application Support/STS/venv-live`; selected model directories were moved alongside it. Setup and the launcher now default there. The source remains in its original repository. This fixes the observed file-hydration launch stall without relying on a cloud-managed virtual environment. The rebuilt environment first completed 63 tests in 6.55 seconds; the final expanded 64-test suite also passed.

## Final implementation changes after hardware qualification

Medium streaming ASR was added after the smaller variants missed a controlled noisy utterance. The final selection combines this recognizer with the same Qwen 2B and fast Piper voice. Manual cross-turn prompt-cache reuse was removed; MLX-LM handles per-response generation state. A targeted model probe identified a separate issue: consecutive user messages after an unspoken cancellation could make Qwen answer the abandoned request. An explicit cancellation control marker resolved that case. A second probe showed missing question punctuation could change the same arithmetic answer; recognized English questions now receive their omitted terminal question mark. These are conversation-format fixes, not hardcoded answers.

The original silent-candidate policy could mute an assistant reply and then let its echo-detection window expire before ASR decoded the echo. Candidates now duck to 25% volume, with a longer recent-output matching window, until recognized new words confirm cancellation. Rendered, ducked phrases remain context; cancelled incomplete phrases do not. Speaker output is bounded to 60 seconds of PCM (about 3.8 MB at 16 kHz float32), covering legitimate long generated replies that exceeded the earlier 20-second bound.

The installed app code and Python caches, as well as model/runtime assets, now reside in Application Support. The repository remains the source of truth; rerun setup after changing serving files. Native default devices refresh between sessions. The acoustic fixture checks per-device mute state: a muted built-in fixture speaker had initially invalidated several runs while USB output remained unmuted. Final tests explicitly enable and restore that speaker. Later tests also used built-in assistant output after the default device changed. Power conditions changed from battery/Low Power Mode during early probes to AC during later hardware runs, so latency improvements cannot be attributed to one code change alone.

## Final audio backend decision

The native speaker path exposed self-echo that text matching alone could not reliably reject. The selected browser path uses real `getUserMedia` audio with WebRTC echo cancellation/noise suppression/gain control and an AudioWorklet for simultaneous capture/rendering. No fake capture device is used. A fast local energy gate reduces playback volume before server recognition completes; the ASR worker confirms new words before invalidating the old reply. Native CoreAudio remains an explicit alternative for comparison/headphone use.

Headless Chromium returned an unsupported audio configuration during this hardware investigation. Tests now run headed Chromium, explicitly remove Chromium's default mute-audio argument, grant this local test origin microphone permission, and report effective track settings. Merely counting generated samples in a muted headless browser would not establish audible hardware output. The fixture speaker's separate hardware mute is also checked and restored.

Synthesis cancellation was removed from the recognition thread: epoch invalidation stops queued output immediately, while the response worker owns potentially blocking synthesis cleanup. Transport backpressure likewise applies to synthesis, not microphone capture. Pure DSP tests verify resampling, capture pacing, acknowledgement order, stale audio rejection, output bounds and local ducking.
